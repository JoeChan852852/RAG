# Tutorial Class Notes: Technical Reading with AI

**Audience:** Engineering students  
**Mode:** Hands-on, experiment-driven tutorial  
**Core idea:** AI can help you search, summarize, compare, and organize technical knowledge — but **you remain responsible for validation, judgment, and ethical use**.

---

## 0. Tutorial Goals

By the end of this tutorial, you should be able to:

| Tutorial Goal | Related CLO |
|---|---|
| Use AI and traditional tools to search for engineering knowledge | CLO 1 |
| Compare AI search with academic/technical search databases | CLO 1, CLO 3 |
| Detect possible AI errors such as hallucinations and overconfidence | CLO 3 |
| Validate mathematical and empirical claims scientifically | CLO 2, CLO 3 |
| Apply the Three-Pass Method to read research papers efficiently | CLO 1, CLO 3 |
| Use human-in-the-loop workflows for safer engineering decisions | CLO 3 |

---

## Class Rules

1. **Do not trust the first answer.**
2. **AI output is a lead, not evidence.**
3. **Every important claim must be traceable.**
4. **For engineering work, unverified claims are dangerous.**
5. **Human judgment is non-negotiable.**

# Section 1: How to Search for Useful Knowledge

## Learning Objective

Learn how to search with purpose, not just with keywords.

---

## 1.1 What Makes Knowledge “Useful” in Engineering?

Useful knowledge should satisfy the **4R Framework**:

| Criterion | Meaning | Student Check |
|---|---|---|
| **Relevance** | Does it answer the engineering question? | “Does this help solve my problem?” |
| **Reliability** | Is it from a trustworthy source? | “Who produced this?” |
| **Recency** | Is it up to date? | “Is this still current?” |
| **Rigor** | Is it supported by proof, data, or method? | “How do they know?” |

---

## 1.2 Shallow Search vs. Deep Search

| Shallow Search | Deep, Purposeful Research |
|---|---|
| Uses one simple query | Starts with a clear question |
| Accepts first result | Compares multiple sources |
| Focuses on speed | Focuses on accuracy |
| Often uses blogs or summaries only | Follows claims back to primary sources |
| Good for quick orientation | Required for engineering decisions |

---

## 1.3 Search Strategy

### Step 1: Define the Information Need

Write your question in this form:

> I need to know **[concept/result/method]** because I want to **[engineering purpose]**.

Example:

> I need to know how vibration sensors detect bridge cracks because I want to evaluate structural health monitoring methods.

---

### Step 2: Turn the Question into Search Queries

| Search Type | Example Query |
|---|---|
| Broad overview | `structural health monitoring overview` |
| Academic | `structural health monitoring vibration sensors review paper` |
| Technical database | `IEEE bridge crack detection accelerometer` |
| AI search | `Explain key methods for bridge crack detection using vibration sensors with sources` |
| Validation | `limitations of vibration-based structural health monitoring` |

---

### Step 3: Refine Iteratively

Use this loop:

```text
Question
   ↓
Search
   ↓
Read results quickly
   ↓
Improve keywords
   ↓
Search again
   ↓
Validate sources
````

***

## Active Learning: Think-Pair-Share

### Prompt

**Premise:** A Google search gives 5 million results. An AI chatbot gives one confident answer.

**Question:** Which one is more trustworthy?

### Individual Thinking: 2 minutes

### Pair Discussion: 3 minutes

### Class Share: 5 minutes

Build a class list:

| Tool               | Advantage | Risk |
| ------------------ | --------- | ---- |
| Traditional search |           |      |
| AI search          |           |      |

### Conclusion

A tool is not trustworthy by itself.  
**Trust comes from source tracing, evidence, and validation.**

# Section 4: Problems AI Search Might Have

## Learning Objective

Identify common AI failure modes in technical reading.

***

## 4.1 Common AI Failure Modes

| Failure Mode                        | Meaning                                       | Engineering Risk                |
| ----------------------------------- | --------------------------------------------- | ------------------------------- |
| **Hallucination**                   | AI fabricates references, equations, or facts | False data enters calculations  |
| **Lack of source traceability**     | AI cannot point to a verifiable source        | Claims cannot be audited        |
| **Recency bias / knowledge cutoff** | AI may miss the latest work                   | Outdated design decisions       |
| **Conflation**                      | AI merges different concepts incorrectly      | Wrong theory applied            |
| **Overconfidence**                  | AI sounds certain even when wrong             | Users stop checking             |
| **Context collapse**                | AI loses nuance in complex reasoning          | Important assumptions disappear |
| **Sycophancy**                      | AI agrees with user’s wrong framing           | Mistakes are reinforced         |

AI hallucination means generating convincing but fabricated or factually incorrect content; source fabrication is a documented risk in academic contexts. [\[pmc.ncbi.nlm.nih.gov\]](https://pmc.ncbi.nlm.nih.gov/articles/PMC11681264/), [\[studyfinds.com\]](https://studyfinds.com/chatgpts-hallucination-problem-fabricated-references/)

***

## 4.2 Concrete Examples

| Example                                       | Possible AI Error                        |
| --------------------------------------------- | ---------------------------------------- |
| “Give me a 2024 IEEE paper proving X.”        | May invent a paper title                 |
| “Derive this equation from Navier-Stokes.”    | May skip invalid assumptions             |
| “This bridge design is safe, right?”          | May agree without engineering validation |
| “Summarize these three papers as one theory.” | May merge incompatible assumptions       |
| “Find the original proof by Pythagoras.”      | May overstate uncertain history          |

# Section 5: How to Validate If a Claim Is Correct

## Learning Objective

Choose the correct validation method for different types of technical claims.

***

## 5.1 General Validation Framework

Use the **T-R-C-C Framework**:

| Step                    | Action                              | Key Question                    |
| ----------------------- | ----------------------------------- | ------------------------------- |
| **Trace the Source**    | Follow the claim back to its origin | Who said it first?              |
| **Review the Evidence** | Examine proof, data, or method      | What supports it?               |
| **Cross-Reference**     | Compare independent sources         | Do others agree?                |
| **Consult Experts**     | Ask qualified people                | What does domain expertise say? |

***

# Type 1: Validating Theoretical and Mathematical Claims

## Core Principle

For mathematics, the gold standard is **proof**.

A mathematical claim is validated when it follows from:

```text
Axioms + Definitions + Prior Theorems + Valid Inference Rules
        ↓
      Claim
```

***

## Mathematical Validation Pattern

```text
Axioms
  ↓
Definitions
  ↓
Prior Theorems
  ↓
Logical Derivation
  ↓
Claim
```

***

## Student Practice

Given the claim:

> For a right triangle with legs `a` and `b` and hypotenuse `c`, `a² + b² = c²`.

Trace:

| Step            | What to Identify                          |
| --------------- | ----------------------------------------- |
| Axioms          | Euclidean geometry assumptions            |
| Definitions     | Right triangle, square, area              |
| Prior theorems  | Congruence, similarity, area rules        |
| Inference rules | Algebraic equality, geometric equivalence |
| Final claim     | `a² + b² = c²`                            |

***

# Type 2: Validating Empirical Claims

## Core Principle

For physical science and engineering claims, proof alone is not enough.

Empirical claims need evidence from the real world.

***

## Empirical Validation Checklist

| Criterion                    | Question                                         |
| ---------------------------- | ------------------------------------------------ |
| **Falsifiability**           | Can the claim be tested or proven wrong?         |
| **Reproducibility**          | Do independent experiments get similar results?  |
| **Statistical significance** | Is the dataset large and robust enough?          |
| **Peer review**              | Has the method been checked by experts?          |
| **Measurement quality**      | Are sensors, instruments, and assumptions valid? |
| **Boundary conditions**      | When does the claim stop being true?             |

***

## Think-Pair-Share: Classify the Claim

### Task

Classify each claim as:

* **Theoretical / mathematical**
* **Empirical / experimental**
* **Mixed**

Then choose the validation method.

| Claim                                                         | Type | Validation Method |
| ------------------------------------------------------------- | ---- | ----------------- |
| `a² + b² = c²` for all Euclidean right triangles              |      |                   |
| This sensor detects cracks with 95% accuracy                  |      |                   |
| This algorithm has time complexity `O(n log n)`               |      |                   |
| This battery lasts 20% longer than the previous design        |      |                   |
| This bridge design satisfies the safety factor requirement    |      |                   |
| A neural network can predict stress concentration from images |      |                   |

***

## Discussion Scaffold

### Premise

Different claims require different evidence.

### Question

Why can’t we validate every engineering claim using the same method?

### Exploration

* Is it a mathematical statement?
* Is it about real-world measurement?
* Does it depend on materials, sensors, or environment?
* Can it fail in practice?

### Conclusion

Use **proof** for mathematical claims.  
Use **experiments and reproducibility** for empirical claims.  
Use **both** for engineering systems.

# Section 7: The Three-Pass Method for Reading Papers

## Learning Objective

Read technical papers efficiently using a structured method.

***

## Source

This section is based on S. Keshav’s paper **“How to Read a Paper,”** which describes a practical three-pass approach to reading research papers. The method recommends reading a paper in up to three passes: first for a general idea, second for content, and third for deep understanding. [\[web.stanford.edu\]](https://web.stanford.edu/class/cs114/reading-keshav.pdf), [\[How to Rea...- SIGCOMM\]](http://ccr.sigcomm.org/online/files/p83-keshavA.pdf)

***

## 7.1 Overview

| Pass            | Goal               | Time         | What You Get                                                      |
| --------------- | ------------------ | ------------ | ----------------------------------------------------------------- |
| **First Pass**  | Bird’s-eye view    | 5–10 min     | Category, context, superficial correctness, contribution, clarity |
| **Second Pass** | Grasp content      | Up to 1 hour | Key arguments, figures, evidence, gaps                            |
| **Third Pass**  | Deep understanding | 1–5 hours    | Reconstruct paper, identify assumptions, critique logic           |

***

# First Pass

## Goal

Decide whether the paper is worth reading deeply.

***

## Checklist

* Read title
* Read abstract
* Read introduction
* Read section and subsection headings
* Read conclusion
* Glance at references

Keshav’s first pass includes reading the title, abstract, introduction, headings, conclusion, and references, and then judging category, context, correctness, contributions, and clarity. [\[web.stanford.edu\]](https://web.stanford.edu/class/cs114/reading-keshav.pdf), [\[How to Rea...- SIGCOMM\]](http://ccr.sigcomm.org/online/files/p83-keshavA.pdf)

***

## First Pass Worksheet

| Question                          | Answer           |
| --------------------------------- | ---------------- |
| What type of paper is this?       |                  |
| What problem does it address?     |                  |
| What is the main contribution?    |                  |
| What evidence or method is used?  |                  |
| Does it seem relevant?            | Yes / No / Maybe |
| Should I continue to Second Pass? | Yes / No         |

***

# Second Pass

## Goal

Understand the main content without getting stuck in details.

***

## Checklist

* Read carefully
* Skip very complex proofs/details at first
* Study figures, diagrams, and tables
* Mark important equations
* Note unfamiliar references
* Write a short summary

***

## Second Pass Worksheet

| Item                  | Notes |
| --------------------- | ----- |
| Main method           |       |
| Key figure/table      |       |
| Main evidence         |       |
| Important assumptions |       |
| Unclear parts         |       |
| References to follow  |       |

***

# Third Pass

## Goal

Understand deeply enough to critique or reproduce the work.

***

## Checklist

* Reconstruct the argument
* Identify stated assumptions
* Identify unstated assumptions
* Check each logical step
* Compare with related work
* Ask what you would do differently

***

## Third Pass Worksheet

| Question                               | Notes |
| -------------------------------------- | ----- |
| Can I reproduce the main argument?     |       |
| Which assumptions are critical?        |       |
| Which steps are weak?                  |       |
| What evidence is missing?              |       |
| How does this connect to other papers? |       |
| What would I improve?                  |       |

***

## Active Task: Apply the Three Passes

### Instructor Setup

Provide one short technical paper or conference paper.

### Student Task

| Stage              | Time   | Output                                 |
| ------------------ | ------ | -------------------------------------- |
| First Pass         | 8 min  | Complete First Pass Worksheet          |

| Second Pass        | 20 min | Complete Second Pass Worksheet         |

# Section 9: Human Intervention vs. AI-Only Flow

## Learning Objective

Understand why human checkpoints are essential in AI-assisted technical reading.

***

## AI-Only Flow

```text
┌─────────────────────────────────────────────────┐
│                 AI-ONLY FLOW                    │
│                                                 │
│ Query → AI Search → AI Summary → AI Analysis    │
│ → AI Conclusion → Output                        │
│                                                 │
│ Risk: Hallucination compounds at each step      │
│ Risk: No reality check                          │
│ Risk: Circular reasoning undetected             │
└─────────────────────────────────────────────────┘
```

***

## Human-in-the-Loop Flow

```text
┌─────────────────────────────────────────────────┐
│             HUMAN-IN-THE-LOOP FLOW              │
│                                                 │
│ Query → AI Search → HUMAN checks sources →      │
│ AI helps organize → HUMAN validates logic →     │
│ AI assists writing → HUMAN reviews final output │
│ → Output                                        │
│                                                 │
│ Each human checkpoint catches errors            │
│ Human provides: judgment, context, ethics       │
└─────────────────────────────────────────────────┘
```

***

## Why Human Intervention Is Non-Negotiable

| Reason                | Explanation                                                  |
| --------------------- | ------------------------------------------------------------ |
| **Judgment**          | AI cannot fully assess real-world consequences               |
| **Accountability**    | A human must own the decision                                |
| **Domain expertise**  | Engineers have tacit knowledge AI lacks                      |
| **Error detection**   | Humans catch subtle nonsense                                 |
| **Ethical reasoning** | AI predicts patterns; humans reason about values             |
| **Safety**            | In safety-critical engineering, unverified AI can cause harm |

***

## Mini-Experiment

### Research Question

> “What are the best AI methods for detecting cracks in bridges using sensor data?”

***

### Flow A: AI-Only

Ask AI:

```text

```

***

### Flow B: Human-in-the-Loop

Use:

1. AI to generate candidate methods
2. Traditional search to verify papers
3. Human reading to check assumptions
4. AI to organize comparison
5. Human final judgment

***

### Comparison Table

| Criterion             | AI-Only Flow | Human-in-the-Loop Flow |
| --------------------- | ------------ | ---------------------- |
| Accuracy              |              |                        |
| Source quality        |              |                        |
| Missing assumptions   |              |                        |
| Practical usefulness  |              |                        |
| Safety risk           |              |                        |
| Confidence justified? |              |                        |

***

## Class Discussion

### Premise

AI can produce fluent answers quickly.

### Question

Does fluency equal reliability?

### Exploration

### Conclusion

The safer workflow is not the fastest workflow.  
Engineering requires **validated confidence**, not just confident language.

# Section 11: Paper A vs. Paper B — Cross-Referencing Framework

## Learning Objective

Compare two technical papers systematically.

***

# 11.1 Axiom-Level Comparison

Use this when papers are theoretical or mathematical.

| Dimension            | Paper A | Paper B | Alignment                     |
| -------------------- | ------- | ------- | ----------------------------- |
| Starting assumptions |         |         | Match / Conflict / Complement |
| Implicit assumptions |         |         | Match / Conflict / Complement |
| Domain of validity   |         |         | Overlap / Disjoint            |
| Definitions          |         |         | Same / Different              |
| Prior theorems used  |         |         | Same / Different              |

***

## Key Questions

1. Do both papers share the same foundational assumptions?
2. Does one paper’s assumption contradict another’s?
3. Could both papers be true at the same time?
4. Are they solving the same problem or different versions of it?
5. Does one paper use a special case of the other?

***

# 11.2 First Principles Comparison

```text
Paper A: First Principles          Paper B: First Principles
          │                                  │
          ▼                                  ▼

          │                                  │
          ▼                                  ▼

          │                                  │
          ▼                                  ▼

```

# 11.5 Practical Cross-Reference Workflow

## Step 1: EXTRACT

List:

* Axioms
* Definitions
* Assumptions
* Methods
* Results
* Limitations

***

## Step 2: MAP

Create a correspondence table.

| Paper A Term | Paper B Term | Same Meaning?    | Notes |
| ------------ | ------------ | ---------------- | ----- |
|              |              | Yes / No / Maybe |       |

***

## Step 3: TRACE

Follow the logical chain:

```text
Axiom → Definition → Lemma → Theorem → Result
```

or, for empirical papers:

```text
Hypothesis → Method → Data → Analysis → Result → Claim
```

***

## Step 4: TEST EQUIVALENCE

Ask:

* Can Paper A’s result be derived from Paper B’s framework?
* Can Paper B’s result be derived from Paper A’s framework?
* Are they equivalent only under special conditions?

***

## Step 5: IDENTIFY THE GAP

Ask:

* What does A cover that B does not?
* What does B cover that A does not?
* What is missing from both?

***

## Step 6: SYNTHESIZE

Ask:

* Can a unified framework include both?
* What new hypothesis emerges?
* What experiment could test the difference?

***

# 11.6 Diagnostic Matrix

|                      | Same Axioms                                                                                         | Different Axioms                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **Same Method**      | Direct comparison. If results differ, check for errors or hidden assumptions.                       | Method may behave differently under different assumptions.              |
| **Different Method** | Strong triangulation if results agree. If results differ, inspect approximation and implementation. | Hardest case. Compare assumptions, methods, and domains before judging. |

# Key Takeaways

* AI is useful for **searching, summarizing, organizing, and questioning**.
* AI is risky when used as an **authority**.
* Mathematical claims require **proof**.
